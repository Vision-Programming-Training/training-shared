## 0. このチェックの位置づけ

課題 A1〜 に入る前の「触りこみ」フェーズの到達確認。点数は付けない。狙いは**課題で詰まる前に、前提知識の穴を見つけること**。

| 部 | 何を確かめるか | 穴があると詰まりやすい課題 |
|---|---|---|
| 第1部 Web 基礎 | URL・メソッド・ステータスコード・クライアント/サーバーの区別 | A6、全般の切り分け |
| 第2部 仕様とデータ | 丸め・単価のスナップショット・JSON | A3 / A7 |
| 第3部 コードの地図 | 3層の責務、症状 → 疑う場所、フロントとの境界 | 全般（どこから読むか） |
| 第4部 テストと開発フロー | テストの赤/緑の意味、ブランチ・PR の作法、再現の意味 | A7 / A8（テストの穴）、PR 作成 |
| 第5部 ハンズオン | 環境・Swagger・DevTools・DB リセット・コードの追跡 | 全般（再現と確認の手段） |

### 課題の答えを漏らさないための設計方針

- 丸めのルール・スナップショットは**受講者ガイドとデータモデルに明記済みの仕様**なので、「仕様を知っているか」は問う。ただし**どのコードで実現しているか**は問わない。
- **例外 → HTTP ステータスの変換箇所（A6 の核）**は問わない。H5 ではエラーレスポンスの形を観察させるだけにしている。
- H8（コード追跡）は `GET /api/orders` の一覧取得にしている。これはどの課題の仕込み箇所とも重ならない。
- 計算問題の数値は、課題の検証値（149 など）と被らないようにしている。

### 回答の見方

- 筆記: 正誤より、**どこが分かっていないか**を見つけるために使う。**言葉が違っても、意味が合っていれば正解**とする。
- ハンズオン: H1〜H9 の**全項目完了が課題に入る条件**。値が違っていたら、その場で一緒に原因を確認する（そこ自体が良い練習になる）。
- 回答を返すときは、間違えた問題を下の「結果別のフォロー」に沿って一緒に確認する。
- **どの部で間違えたか**に注目する。第2部を落とした人は A3・A7 で、第3部を落とした人は全課題の「どこから読むか」で詰まりやすい。

## 第2部 アプリの仕様とデータ

### Q2-1

215 × 1.10 = **236.5** → 1円未満を四捨五入（.5 は切り上げ）→ **237円**。

- 236 と答えた人は「.5 は切り上げ」を読み落としている（切り捨て・偶数丸めの発想）。A7 の前に必ずフォローする。

### Q2-2

(a) **300円**（①で注文したときの価格のまま）。②で商品マスタが500円になっても、注文Xには影響しない。

(b) 明細の単価は、**注文確定時の価格をコピーしたスナップショット**として保存しているから。後から商品マスタの価格が変わっても、過去の注文の金額は変わらない。

- 「スナップショット」「注文時点の価格を保存」の趣旨が書けていれば正解。
- 「500円になる」と答えた人は、A3（★★★）で設計意図が読めずに詰まる可能性が高い。データモデル §2 の不変条件を一緒に読む。

### Q2-3

(a) **2件**（`items` 配列の要素数）

(b) **クーポンを使っていない**注文である。

(c) `unitPrice × quantity`（明細ごとの税抜小計）

(d) **税込**（1800 + 300 = 2100 → × 1.10 = 2310）

- 根拠はデータモデルの `Order.TotalAmount`（「確定時の税込合計」）か、バックエンド README の注文作成の説明。資料を見ずに、`lineTotal` の合計と比べて気づけていてもOK。

## 第3部 コードの地図

### Q3-1

| 層 | 正解の趣旨 |
|---|---|
| Controller | リクエストを受けて Service に渡し、結果を返すだけの入口。**ロジックも例外処理も書かない**（薄く保つ） |
| Service | 業務ロジックの中心。金額計算・クーポン・在庫・注文/キャンセルなど |
| Repository | DB へのアクセス（読み書き）だけを担当する |

### Q3-2

| 症状 | 正解 | 理由 |
|---|---|---|
| (a) 割引額が仕様と違う | **Service** | 計算ロジックは Service にある |
| (b) ボタンを押しても通信が発生していない | **フロント（HTML/JS）** | リクエストがサーバーに届いていない＝サーバー以前の問題 |
| (c) 在庫が0と出るが、コードは変更されていない | **DB の中身** | 表示もAPIも一致しており、コードの変更もない → データそのものを疑う |

> (b) は「Network タブに通信が出ていない」がポイント。**通信が出ているかどうかで、フロントかサーバーかを切り分ける**考え方ができているかを見る。

### Q3-3

(a) `js/core/api.js`

(b) `js/core/config.js`（`API_BASE_URL`）

### Q3-4

フロントとサーバーは**ポートが違うので、別のオリジン**になる。ブラウザは同一オリジンポリシーによって、別オリジンへの `fetch` を原則ブロックする。そのため、サーバー側で「このフロントのオリジンからのアクセスは許可する」という CORS の設定が必要になる。

- 「オリジン（またはポート）が違うから」＋「ブラウザがブロックする」の2つが書けていれば十分。

## 第4部 テストとチーム開発

### Q4-1

(a) 緑＝テストが期待する（仕様どおりの）動きをしている。赤＝どこかが仕様どおりに動いていない。

(b) 自分の修正が、**それまで動いていた別の機能を壊した（デグレ）**。修正の仕方を見直し、全テストが緑になるまで直す。赤いテストを消したり、期待値を書き換えて緑にしたりしてはいけない。

- 「テストを消す／期待値を書き換える」と答えた場合は、必ず口頭でフォローする。

(c) **起こり得る**。テストは書かれたケースしか確かめないので、**テストが試していない入力**のバグは見逃される。

- A7・A8 の前提になる感覚。「起こらない」と答えた人は A7・A8 の前に補足する。

### Q4-2

(a) 課題ブランチは**全員が共有して使うもの**なので、直接変更すると他の人に影響が出る（配布状態が壊れる）から。

(b) `fix/`

(c) 再現できないと、**原因を正しく特定できたか**も、**本当に直ったか**も確かめられないから。

### Q4-3

- 何を変えたか
- どう確認したか
- 影響範囲

## 第5部 ハンズオン（言語非依存の正解値）

> 初期データ（seed）の状態から、H1〜H9 を**順番どおりに**行った場合の値。途中で別の注文をしていると在庫数などがずれるので、ずれていたら理由を一緒に確認する。

| 項目 | 期待される結果 |
|---|---|
| H1 | Swagger UI・フロントの URL は言語版の付録を参照。フロントの商品一覧が表示されればOK |
| H2 | 言語版の付録を参照（全件成功が正解） |
| H3 | `200`、商品 **7 件**、ステッカーの在庫 **0** |
| H4 | リクエスト例 `{ "items": [{ "productId": 1, "quantity": 2 }] }`（`couponCode` は省略・`null`・空文字のどれでも可）<br>ステータス **201**、`totalAmount` **660**、ノートの在庫 **50 → 48** |
| H5 (a) | **404**、「商品が見つかりません」という趣旨のメッセージ |
| H5 (b) | **400**、「在庫が不足しています（商品・在庫・要求数）」という趣旨のメッセージ。ボールペンの在庫は **100 のまま変わらない** |
| H6 | `POST` で `<API のベース URL>/api/orders` に送られ、ステータスは **201** |
| H7 | ステータス **Cancelled**、在庫は**元に戻る**。2回目のキャンセルは **400**（「既にキャンセル済み」） |
| H8 | 言語版の付録を参照。**Controller → Service → Repository** の順に書けていればOK |
| H9 | DB を初期化して再起動した。ノートの在庫 **50** |

### ハンズオンで見るポイント

- **H5 のエラーの形**: エラーレスポンスが `{ "status": ..., "error": "..." }` という JSON で返ることに気づけているか。A5・A6 で症状を観察するときの前提になる。
- **H5 (b) の在庫**: 失敗した注文で在庫が減っていないことを確認できているか。「エラーのときに中途半端な状態が残っていないか」を見る観点を身につけさせたい。
- **H6**: 画面の操作と、Swagger で叩いた API が**同じもの**だと結び付いているか。
- **H8**: ファイル名だけでなく、層の順番を意識して書けているか。途中の変換（エンティティ → DTO）まで書けていれば褒める。
